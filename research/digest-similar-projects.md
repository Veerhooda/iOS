# Digest: similar projects — boot_args + device tree + framebuffer staging, early-boot-hang debugging

Context: XNU / iOS bring-up on non-Apple ARM hardware (our target: OnePlus 2, Snapdragon 810 MSM8994).
Each claim carries its source URL. Fetched 2026-11-02/03.

---

## 1. dipa-studio/ios-sweet — XNU (xnu-8796, iOS 16) on Redmi Note 10 Pro (sweet, SM7150 / Snapdragon 732G)

Closest analogue: XNU + unmodified iPhone X iOS 16.7.16 userland on a Qualcomm phone; boots to home screen.

- Boot chain is stock Xiaomi ABL (unlocked) → `fastboot boot shim-boot.img` (nothing flashed) → bare-metal shim (own MMU setup, reads the live FDT, loads payload from ramdisk) → XNU Mach-O + generated Apple Device Tree (ADT) + boot-args → UFS driver → HFS+ root in `userdata` → dyld/shared cache → launchd → backboardd + SpringBoard.
  Source: https://raw.githubusercontent.com/dipa-studio/ios-sweet/main/README.md
- The ADT is generated by `tools/mkadt.py` from sweet's MMIO layout plus the iPhone X identity (`iPhone10,3` / `D22AP`); `tools/mkpayload.py` packs kernel + ADT + boot-args into the shim payload.
  Source: https://raw.githubusercontent.com/dipa-studio/ios-sweet/main/README.md
- Staged boot-args and their roles: `rd=ufsroot0 ufsrw=1 rootrw=1` (writable root on userdata), `cpus=6` with `cpus=1` as safe fallback, `launchd_unsecure_cache=1` (launchd accepts job cache without AMFI), `wdt=-1 wdt_test=no_user_checkin` (no hardware watchdog), `sweetfb_noconsole=1` (stop drawing kernel text over the GUI; text still goes to the persistent log, panics still drawn), `sweetfb_hz=30` (CPU-copy panel refresh), `sweettouch=0` / `sweetkeys=0` (disable touch/button drivers).
  Source: https://raw.githubusercontent.com/dipa-studio/ios-sweet/main/README.md
- Framebuffer staging: no serial port (debug UART wired as SPI), so the kernel draws its console into the bootloader framebuffer ABL leaves at `0x9c000000` (early framebuffer console, patches 0010–0018); later IOSurface (`IOCoreSurfaceRoot`) + IOMobileFramebuffer (`AppleCLCD`) services with CoreAnimation software rendering, frames copied into the bootloader's framebuffer and presented to iOS as an iPhone X panel (1125×2436); throttled panel copy (patches 0056–0057, 0061).
  Source: https://raw.githubusercontent.com/dipa-studio/ios-sweet/main/README.md
- Early-boot-hang debugging without serial: a persistent 4 MiB log ring at the end of `userdata`, pulled from OrangeFox recovery with `tools/sweet-log-pull.sh`; log holds `CRASH name …` reports with backtraces, IOKit traces of backboardd/SpringBoard, and drivers' `SWEET …` lines; `tools/sweet-crash.py` symbolicates against the shared cache; `tools/qemu-sweet.py` boots the same kernel on QEMU `virt` with framebuffer text decoding for kernel-only changes; first boot takes ~4–5 min on the Apple logo (slow boot is normal, not a hang signature by itself).
  Source: https://raw.githubusercontent.com/dipa-studio/ios-sweet/main/README.md
- Hardware facts reused from Qualcomm/Linux sources: payloads in upper DDR bank `0x100000000 + 0xfcc00000`; GICv3 timer via Group 1 IRQ virtual timer INTID 19, not FIQ as on Apple silicon; PSCI via `smc`, 19.2 MHz timer, ARMv8.2 without PAC, MPIDR Aff1 = core number; panel 1080×2400 DSC video mode with continuous splash from ABL (no refresh kick needed).
  Source: https://raw.githubusercontent.com/dipa-studio/ios-sweet/main/README.md
- Relevant forks proving the pattern ports across Snapdragon SoCs: OnePlus 6T (SDM845, `fajita`) boots to home screen; Galaxy S9 (SDM845) boots jailbroken; Redmi Note 12 4G (SM6225) boots to home screen.
  Sources: https://github.com/edi194/ios-fajita, https://github.com/syncmodz/ios-s9, https://github.com/wlw333554/ios-topaz

## 2. Corellium Project Sandcastle — Android/Linux on iPhone 7 (A10) via checkm8/checkra1n

Reverse direction (foreign kernel on Apple SoC), but the staging pieces mirror ours.

- `loader/` loads the kernel and device tree via pongoOS: `load-linux.c` finds the pongo USB device (VID `0x05ac`, PID `0x4141`), bulk-transfers the DTB then issues the `fdt` shell command, bulk-transfers the kernel image then issues `bootl`.
  Sources: https://raw.githubusercontent.com/corellium/projectsandcastle/master/README.md, https://raw.githubusercontent.com/corellium/projectsandcastle/master/loader/load-linux.c
- A custom device tree ships in the Sandcastle distribution because Apple's own FDT generator output is basic (framebuffer + display only).
  Source: https://news.ycombinator.com/item?id=22493274 (comment thread; secondary source, not officially confirmed)
- Kernel comes from Corellium's `linux-sandcastle` fork of linux-stable; the Linux ramdisk is built with buildroot (`sandcastle-buildroot`); userland binaries must be rebuilt for 16 KB pages (`-z common-page-size=0x4000 -z max-page-size=0x4000`, RELRO/LOAD 16K alignment checked with `readelf -l`).
  Source: https://raw.githubusercontent.com/corellium/projectsandcastle/master/README.md
- Device support is narrow (CPU support only on iPhone 7 / 7+; project inactive since March 2020); `syscfg/` tool extracts config info from the syscfg partition; `hx-touchd` / `hcdpack` cover touch and Bluetooth firmware.
  Sources: https://theapplewiki.com/wiki/Project_Sandcastle, https://raw.githubusercontent.com/corellium/projectsandcastle/master/README.md

## 3. checkra1n / pongoOS boot chain — DTB patching, boot-args, kernel load

- Chain: checkm8 BootROM exploit → pongoOS (AArch64 pre-boot environment for A7–A11, lives only in RAM) → Kernel Patch Finder (KPF) scans and patches the kernel in memory → hands off to patched XNU, or to a Linux kernel. `checkra1n -k Pongo.bin` drops to the pongo shell; `-k PongoConsolidated.bin` auto-runs KPF and boots XNU; with `-p` it loads KPF but stops at the shell.
  Sources: https://raw.githubusercontent.com/checkra1n/PongoOS/master/README.md, https://medium.com/@JanCSG/inside-checkra1n-a-deep-dive-into-the-checkm8-exploit-and-pongoos-internals-2cb8e7261839, https://github.com/34306/ios-exploit-starterpack/blob/HEAD/en/checkm8.md
- pongoOS patches the device tree and the kernel boot-arguments structure (e.g. to map an embedded ramdisk as root) before kernel handoff.
  Source: http://yungraj.com/checkra1n/
- Linux-boot module (`src/modules/linux/linux.c`, with libfdt): builds an empty FDT from the Apple device tree (`compatible = "apple,<soc>"`, `hx,v1` CPUs, `refclk24mhz` fixed clock, `arm,armv8-timer`, memory range from `gBootArgs->memSize`, reserved `nomap` area); default `/chosen/bootargs` is `debug earlycon=hx_uart,<uart0+IOBase> console=tty0 console=ttyHX0`; the `linux_cmdline` shell command overrides it via an overlay (delete + re-append `bootargs`); `fdt` uploads a DTB pack (per-device selection by key); `bootl` LZMA-decompresses the kernel, stages image + DTB at entry `0x800080000` per the ARM64 Linux boot protocol, and applies iPhone 7 display pixel-format/colormatrix register tweaks for the framebuffer.
  Sources: https://raw.githubusercontent.com/checkra1n/PongoOS/master/src/modules/linux/linux.c, https://github.com/A11pwnX/Linux-iPhone-6s-X-howto (load_linux.py flow: kernel Image.lzma + dtbpack + initramfs), https://github.com/big-dick-tech/iphone7plus-uefi (x0=DTB, entry at 0x800080000)
- Debugging is over the USB pongo shell (`pongoterm` client in `scripts/`); gotcha: recent pongoOS builds removed the Linux commands (`linux_cmdline`, `fdt`, `bootl`), so a `Bad command: linux_cmdline` response means the on-device pongo build predates/lacks them.
  Sources: https://raw.githubusercontent.com/checkra1n/PongoOS/master/README.md, https://github.com/jacopone/ipad-nixos

## 4. openiBoot (iDroid Project, planetbeing; maintained mirror iProgramMC/openiBoot)

- Open-source bootloader chainloaded from Apple's iBoot (recovery mode via an img3 image, DFU mode via a raw bin); per-device builds (`scons iPhone2G/iPhone3G/iPhone4/…`); GRUB-style configurable menu in `/boot/menu.lst` with entries naming a kernel plus command line (e.g. `kernel "(hd0,1)/idroid/zImage" "console=tty root=/dev/ram0 init=/init rw"`) and an initrd — i.e. boot-args are staged as menu-entry strings.
  Source: https://raw.githubusercontent.com/iProgramMC/openiBoot/master/README.md
- Framebuffer console: `framebuffer.c` registers a printf handler (`addPrintfHandler(framebuffer_printf_handler)`) that renders boot text onto the LCD via platform `lcd_*` drivers (font blitting through `PixelFromCoords`, `lcd_fill` clear), with `framebuffer_setdisplaytext()` to mute text while keeping the chained `prev_printf_handler` alive — the same "console-to-FB plus mute flag" pattern ios-sweet later used (`sweetfb_noconsole`).
  Source: https://raw.githubusercontent.com/iProgramMC/openiBoot/master/framebuffer.c
- Debug surface is the on-device console (interactive `commands.c` shell) plus USB client tools and udev rules for host communication; repo also carries `nvram.c`, `syscfg.c`, NAND/NOR, and per-SoC platform dirs (`plat-s5l8900/…`).
  Sources: https://raw.githubusercontent.com/iProgramMC/openiBoot/master/README.md, https://api.github.com/repos/iProgramMC/openiBoot/contents (tree listing showing `framebuffer.c`, `menu`, `nvram.c`, `plat-s5l*`)

## 5. XNU/Linux on Snapdragon 810 (MSM8994) and GICv2 + XNU work

- Mainline `msm8994.dtsi` (authoritative for our SoC family): interrupt controller `intc: interrupt-controller@f9000000`, `compatible = "qcom,msm-qgic2"` (GICv2, no redistributors), `reg = <0xf9000000 0x1000>, <0xf9002000 0x1000>` (distributor + CPU interface); 8 CPUs (4× Cortex-A53 + 4× Cortex-A57) with `enable-method = "psci"`; `psci { compatible = "arm,psci-0.2"; method = "hvc"; }`; XO clock 19.2 MHz; `interrupt-parent = <&intc>`; memory `reg` expected to be filled in by the bootloader.
  Source: https://raw.githubusercontent.com/torvalds/linux/master/arch/arm64/boot/dts/qcom/msm8994.dtsi
- UniXNU-lumia950 (MSM8992 = `msm8994.dtsi` minus two A57 cores; Lumia 950): boots through the phone's own UEFI → `UniXNU.efi` menu → `DarwinBoot.efi` loader → `kernel.macho` + generated `.adt` sidecar (`make-lumia950-adt.py`, re-validated by `check-adt.py`; a kernel without its `.adt` is refused before anything is copied to the phone). Its XNU GICv2 interrupt path "accepts the ADT's `qcom,msm-qgic2` node and boots under QEMU"; the register map (SDHCI, GIC, GCC/MMCC/TLMM/APCS/RPM windows, SPI numbers) is taken straight from the mainline MSM8992/MSM8994 device tree; display bring-up is staged in rungs (map MDP/MMSS/DSI0/PHY, prove power domain on, read revisions — publish no framebuffer until later rungs).
  Source: https://raw.githubusercontent.com/manguy-legend/unixnu-lumia950/main/README.md
- UniXNU hang signatures relevant to us: screen stays black after the boot entry + reset seconds later = kernel started and stopped, watchdog reset, nothing drawable after `ExitBootServices`; MSM8992 has no PSCI `SYSTEM_RESET`/`SYSTEM_OFF`, so reset entries fall back to firmware `ResetSystem`.
  Source: https://raw.githubusercontent.com/manguy-legend/unixnu-lumia950/main/README.md
- No public complete XNU-on-MSM8994 bring-up was found beyond the above (MSM8992 sibling + mainline DT); GICv2 + XNU specifics live in the UniXNU kernel tree, not the device repo README.

## 6. OpenCore — boot-arg / device-property handling for hangs (x86 Hackintosh, technique transfers)

- Debug boot-args set under `NVRAM → Add → 7C436110-AB2A-4BBB-A880-FE41995C9F82 → boot-args`: `-v` (verbose), `keepsyms=1` (keep symbols in panics), `debug=0x100` (disable watchdog reboot on panic) or `debug=0x12a` (`DB_PRT|DB_KPRT|DB_SLOG|DB_LOG_PI_SCRN`), `msgbuf=1048576` (1 MB kernel message buffer for early logs), plus situational `serial=5` (early serial output), `io=0xff`, `igdebug=0xff`, `-liludbgall`, `acpi_layer`.
  Sources: https://dortania.github.io/OpenCore-Install-Guide/troubleshooting/kernel-debugging.html, https://github.com/dortania/opencore-install-guide/blob/HEAD/troubleshooting/kernel-debugging.md, https://deepwiki.com/dortania/OpenCore-Install-Guide/7-troubleshooting
- OpenCore `Debug` section for early hangs: `AppleDebug=YES` (boot.efi logging, 10.15.4+), `DisableWatchDog=YES` (UEFI watchdog off), `Target=67` (`75` adds serial `0x08`), `Misc→Serial→Init=YES` to get OpenCore logging onto serial.
  Sources: https://dortania.github.io/OpenCore-Install-Guide/troubleshooting/kernel-debugging.html, https://dortania.github.io/OpenCore-Install-Guide/config.plist/ivy-bridge.html
- `DeviceProperties → Add → PciRoot(…)` injects per-device properties consumed by WhateverGreen+Lilu: `device-id` spoofing, `AAPL,ig-platform-id`, `framebuffer-patch-enable`, `framebuffer-stolenmem`/`framebuffer-fbmem`/`framebuffer-unifiedmem` (VRAM sizing); wrong framebuffer properties are a classic "verbose OK then black screen" hang signature, debugged with `-v` + iGPU debug flags.
  Sources: https://dortania.github.io/OpenCore-Post-Install/gpu-patching/intel-patching/vram.html, https://deepwiki.com/sqlsec/Hackintosh/4.1-graphics-and-display-configuration, https://tonymacx86.com/threads/patching-intel-hd-4400-through-whatevergreen-stops-big-sur-from-booting.325644/
- `DebugEnhancer.kext` raises `kern.msgbuf` to ~10 MB but only loads just before PCI configuration, so early kernel logs still require the `msgbuf=` boot-arg; `SSDT-DBG` enables ACPI-table debug statements.
  Source: https://dortania.github.io/OpenCore-Install-Guide/troubleshooting/kernel-debugging.html

## Takeaways for OnePlus 2 (MSM8994) XNU bring-up

1. Follow the ios-sweet staging split: shim reads live FDT → generate ADT from MMIO layout + spoofed iPhone identity → pack kernel + ADT + boot-args (`mkadt.py`/`mkpayload.py` pattern).
2. Expect GICv2 (`qcom,msm-qgic2` at `0xf9000000`/`0xf9002000`), PSCI `hvc`, 19.2 MHz XO, A53+A57 clusters from `msm8994.dtsi`; UniXNU's GICv2 XNU path + QEMU is the nearest proven interrupt reference.
3. No serial ⇒ framebuffer console inherited from the bootloader + persistent log ring + `cpus=1` / driver-disable boot-args + QEMU-with-FB-decode is the proven debug loop (ios-sweet); openiBoot's chained FB printf handler is the minimal version of the same idea.
4. Borrow OpenCore's hang triage vocabulary: `-v`-equivalent verbose, keep symbols, disable watchdog reboot, enlarge msgbuf, and treat "verbose OK then black screen" as a framebuffer/device-property fault, not a dead kernel.
